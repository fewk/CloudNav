# 点击次数统计与排序功能设计方案（留档记录）

> **状态**：已完成技术方案评估与架构设计，暂缓实现，留档供后续版本排期迭代。

---

## 1. 需求概述
* **目标**：统计用户对各个站点卡片的点击/使用频次，支持在导航页按点击次数从高到低排序，使用户高频访问的站点能够自动排在前面。
* **用户价值**：减少在层层分类中查找高频站点的步骤，打造贴合个人日常习惯的“智慧导航”。

---

## 2. Cloudflare 平台架构权衡

| 架构方案 | 数据写入机制 | 优点 | 缺点 / 限制 | 推荐度 |
| :--- | :--- | :--- | :--- | :--- |
| **方案 A：纯实时 Workers KV** | 每次点击实时向 KV 发起一次 `put` 写入 | 实时多端同步 | **突破配额**：KV 免费额度仅 1,000 次写入/天，频繁点击易耗尽；全量重写 `app_data` 易产生并发覆盖冲突 | ❌ 不推荐 |
| **方案 B：Local-First + 防抖批量同步（推荐）** | 本地 `localStorage` 记录点击瞬间响应；累积 10 次或每隔 5 分钟批量同步至 KV | 零点击延迟、零卡顿；每日消耗极少量 KV 写入；无网络断网时仍可使用 | 极短时间内多端数据有微小同步延迟（对个人导航站完全可忽略） | ⭐⭐⭐⭐⭐ **首选落地** |
| **方案 C：Cloudflare D1 (Serverless SQLite)** | 每次点击调用 D1 接口：`UPDATE links SET clicks = clicks + 1 WHERE id = ?` | D1 免费额度高达 100,000 次写入/天；支持原子计数器 | 架构需引入并迁移至 D1 关系型数据库，复杂度较高 | ⭐⭐⭐ 可做未来演进 |

---

## 3. 详细数据结构设计（建议）

在 `types.ts` 的 `LinkItem` 中新增：
```typescript
export interface LinkItem {
  // ... 既有字段
  clickCount?: number;      // 累计点击次数
  lastClickedAt?: number;   // 最后一次访问时间戳（用于防止老旧站点永久霸榜）
}
```

---

## 4. 进阶推荐设计

1. **“高频常用 Top 10” 动态虚拟分类 / 首页快捷区**：
   * 在首页顶部或侧边栏新增“🔥 高频常用”区域，自动提取点击前 10~15 个站点，免去手动查找。
2. **时间衰减算法（最近常用 vs 历史常用）**：
   * 排序支持切换：“历史总计最高” 与 “最近高频访问”（结合 `lastClickedAt` 计算热度分）。
3. **搜索框联想提权**：
   * 搜索匹配时，点击次数越多的站点优先排在前面，支持回车秒开。
